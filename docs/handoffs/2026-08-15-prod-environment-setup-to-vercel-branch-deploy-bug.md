## Where things stand

- **L'environnement de prod existe et fonctionne de bout en bout** (hors paiement réel, voir plus bas) :
  - Backend Medusa sur Railway, projet `khn-prod`, service `khn-dev` — `https://khn-dev-production-fc9e.up.railway.app`, `/health` → `200`.
  - Postgres + Redis Railway, migrés, seedés, vrai catalogue importé.
  - Storefront Next.js sur Vercel, projet `khn-prod` — `https://khn-prod.vercel.app` (domaine provisoire, `kim-hi-noodle.fr` n'est pas encore basculé).
  - Admin Medusa prod accessible (`toshouw@gmail.com`, mot de passe connu de l'utilisateur uniquement).
- **Séparation staging/prod au niveau des déploiements automatiques** : les deux environnements Railway et Vercel suivent maintenant des branches Git différentes — `main` pour staging (comportement inchangé), **`production`** (nouvelle branche) pour prod. Un merge sur `main` ne redéploie donc plus prod par accident. `main` et `production` sont actuellement strictement synchronisées sur le même commit (`f7d5eed`).
- **Catalogue réel importé en prod** : 42 produits + 6 Formules (export depuis la base locale via `export-menu-data.ts`, import via `import-menu-data.ts`), puis **nettoyage explicite des 4 produits de démo du starter** (T-shirt/Sweatshirt/Sweatpants/Shorts) — contrairement à staging où ils traînent encore, jamais nettoyés.
- **Quatre bugs réels découverts et corrigés cette session, tous mergés sur `main` ET propagés sur `production`** (PRs [#133](https://github.com/ThomasOk/khn-dev/pull/133), [#134](https://github.com/ThomasOk/khn-dev/pull/134), [#135](https://github.com/ThomasOk/khn-dev/pull/135), [#136](https://github.com/ThomasOk/khn-dev/pull/136)) — détail dans "Ce qui s'est passé".
- **R2** : bucket `khn-images` réutilisé (pas de raison de dupliquer, voir justification plus bas), nouveau token API dédié prod (`khn-medusa-prod`).
- **Resend** : nouvelle clé API dédiée prod, domaine `mail.kim-hi-noodle.fr` réutilisé tel quel (déjà vérifié).
- **Stripe** : clé secrète live dédiée créée, `webhookSecret` câblé dans le code (était absent, touchait aussi staging), endpoint webhook enregistré en mode live (`/hooks/payment/stripe_stripe`), `STRIPE_WEBHOOK_SECRET` posé sur Railway. **Le test de paiement réel (checklist section 4, dernier point) n'a pas encore été fait** — on s'est arrêté juste avant, après avoir découvert et corrigé le bug du provider de paiement (voir plus bas).
- **Bloqué en fin de session sur un problème de déploiement automatique Vercel** : les push sur la branche `production` ne déclenchent pas de déploiement Vercel automatique (alors que Railway, lui, redéploie correctement à chaque fois). Contournement fonctionnel mais manuel : le Deploy Hook Vercel (Settings → Git → Deploy Hooks). Piste de correctif proposée mais **pas encore décidée par l'utilisateur** (voir "Problèmes identifiés").

## Ce qui s'est passé

**1. Provisioning Railway prod** : nouveau projet `khn-prod` (même compte Railway dédié que staging), services Postgres + Redis ajoutés, puis service backend `khn-dev` lié au repo GitHub. Root Directory laissé à la racine, Build/Start Command identiques à staging (`pnpm turbo run build --filter=@dtc/backend && cd apps/backend/.medusa/server && pnpm install --no-frozen-lockfile` / `cd apps/backend/.medusa/server && npm run start`).

**2. Séparation staging/prod par branche** — décision prise avant de commencer, pour éviter qu'un merge sur `main` ne redéploie les deux environnements en même temps : création d'une branche `production` (depuis `main`), service Railway prod reconfiguré pour suivre `production` au lieu de `main` (Settings → Source → "Branch connected to production"). Même chose côté Vercel plus tard (Settings → Environments → Production → Branch Tracking).

**3. Variables d'environnement backend** : `DATABASE_URL`/`REDIS_URL` via référence Railway (`${{Postgres.DATABASE_URL}}` etc.), `JWT_SECRET`/`COOKIE_SECRET` régénérés (distincts de staging), `NODE_ENV=production`, `ADMIN_CORS` (domaine backend), puis complétés au fil de la session (S3_*, RESEND_*, STRIPE_*, STORE_CORS/AUTH_CORS/STOREFRONT_URL une fois l'URL Vercel connue).

**4. Premier crash au démarrage — tables inexistantes** : migrations lancées depuis le poste local avec `DATABASE_URL="<DATABASE_PUBLIC_URL>" pnpm --filter @dtc/backend db:migrate` (Public Access activé sur le Postgres prod pour obtenir cette URL — l'interface Railway a changé depuis staging, propose maintenant aussi un tunnel chiffré via `railway connect`, mais la CLI installée ici — 4.35.1 — ne supporte pas le flag `--tunnel-only` vu dans le dashboard ; on est resté sur Public Access, comme pour staging).

**5. Deuxième crash — R2 non configuré** : `Access key ID and secret access key are required`. Le module fichier S3/R2 est enregistré de façon inconditionnelle dans `medusa-config.ts` (code partagé), donc il **doit** avoir les variables `S3_*` pour démarrer, même avant d'avoir traité "la phase R2" de la feuille de route. Décision prise avec l'utilisateur : réutiliser le bucket `khn-images` existant plutôt qu'en créer un nouveau — **pas pour une raison de coût** (R2 est largement dans son tier gratuit à cette échelle), mais parce que les URLs d'images des 42 produits importés pointent **littéralement** vers ce bucket précis (copiées telles quelles depuis la base locale, migrées en R2 le 05/08) ; un bucket "dédié prod" ne migrerait pas ces fichiers, juste les futurs uploads. Nouveau token API dédié (`khn-medusa-prod`, Object Read & Write, scopé à `khn-images` uniquement) créé via **R2 Object Storage → Overview → Account API Tokens** (l'interface Cloudflare a changé, plus de bouton "Manage API Tokens" au niveau du bucket).

**6. Seed + import du vrai catalogue** :
   - `pnpm seed` lancé contre la base prod (crée l'infra nécessaire : sales channel, région FR, TVA, **mais aussi** les 4 produits de démo — inévitable, `seed.ts` les crée toujours).
   - `import-menu-data.ts` rejoué contre prod (nécessite un nouveau snapshot — l'ancien `tmp/menu-snapshot.json` n'est pas committé — régénéré via `export-menu-data.ts` contre la base **locale**) : 42 produits créés, 6 Formules, TVA 20% Alcool créée, stock location réelle créée et fulfillment set repointé depuis l'entrepôt démo.
   - **Nouveau script committé `cleanup-demo-data.ts`** (pattern `fix-tax-default.ts` : petit, idempotent, réutilisable) pour supprimer les 4 produits de démo — testé d'abord en local (bloqué par une réservation d'inventaire résiduelle, sans rapport, local laissé tel quel), puis exécuté avec succès contre prod. **PR #133, mergée et propagée.**

**7. Admin user créé** (`medusa user`, skill `medusa-dev:new-user`), clé publiable récupérée depuis `/app` → Settings → Publishable API Keys.

**8. Bug Redis découvert en lisant les logs de boot** (`redisUrl not found. A fake redis instance will be used.` + `Local Event Bus installed. This is not recommended for production.`) — **préexistant, touche staging autant que prod**, jamais corrigé jusqu'ici :
   - `projectConfig.redisUrl` jamais renseigné → sessions HTTP admin en `MemoryStore` (perdues à chaque redéploiement).
   - Aucun module `cache-redis`/`event-bus-redis`/`workflow-engine-redis` enregistré → event bus en mémoire locale, qui peut silencieusement perdre l'événement `order.placed` (email de confirmation, ticket cuisine) si le process redémarre au mauvais moment.
   - Corrigé dans `medusa-config.ts`, activé uniquement quand `REDIS_URL` existe (aucun effet sur le dev local sans Redis). Piège trouvé en cours de route : `workflow-engine-redis` attend ses options sous une clé imbriquée `redis: { redisUrl }`, contrairement aux deux autres modules qui prennent `redisUrl` directement — trouvé en lisant le code source du loader après un premier crash.
   - **PR #134, mergée, testée en conditions réelles sur staging (4 connexions Redis confirmées dans les logs, `/health` OK) avant propagation vers prod.**

**9. Bug `webhookSecret` Stripe manquant**, visible dans les logs depuis le tout début (`Option webhookSecret is missing in Stripe plugin...`) — câblé dans `medusa-config.ts` (`webhookSecret: process.env.STRIPE_WEBHOOK_SECRET`). URL exacte du webhook trouvée en vérifiant l'ID réel du provider en base (`select id from payment_provider` → `pp_stripe_stripe`) contre la convention `"pp_" + eventData.provider` du code source Medusa : `/hooks/payment/stripe_stripe`. Endpoint enregistré côté Stripe (mode live, nouvelle interface "Destinations d'événements") avec 5 événements (`payment_intent.succeeded/payment_failed/canceled/amount_capturable_updated`, `charge.refunded`). **PR #135, mergée et propagée.**

**10. Test du paiement réel commencé, bug bloquant découvert** : sur la page de checkout prod, seul "Paiement manuel" apparaissait, pas le formulaire carte Stripe — **le même problème existait déjà sur staging** au tout début (06/08). Diagnostic (comparaison staging/prod en base, table `region_payment_provider`) : `seed.ts` ne lie que `pp_system_default` (paiement manuel) à la région France, jamais Stripe. Sur staging, corrigé à la main dans l'admin le 06/08 (Stripe ajouté, paiement manuel retiré) mais **jamais reporté dans `seed.ts`** — donc prod, fraîchement seedée, a reproduit exactement le même trou de départ. Corrigé : `seed.ts` (`payment_providers: ["pp_stripe_stripe"]`) + nouveau script `fix-region-payment-provider.ts` (pattern `fix-tax-default.ts`), testé en local (déjà dans le bon état, no-op confirmé) puis exécuté avec succès contre prod. **PR #136, mergée et propagée.**

**11. Déploiement Vercel du storefront prod** : projet créé (Root Directory `apps/storefront`), variables `NEXT_PUBLIC_MEDUSA_BACKEND_URL`/`NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY`/`NEXT_PUBLIC_DEFAULT_REGION=fr`/`NEXT_PUBLIC_ALLOW_INDEXING=true`/`NEXT_PUBLIC_BASE_URL` (provisoire, `https://khn-prod.vercel.app`) posées avant le premier déploiement, `NEXT_PUBLIC_STRIPE_KEY` (clé publiable live) ajoutée directement par l'utilisateur dans le dashboard. Premier déploiement réussi, vrai contenu affiché (photos, catalogue réel via SSR — vérifié par `curl`).

**12. Découverte et tentative de correction du bug de déploiement auto Vercel** — voir "Problèmes identifiés, non résolus" pour le détail complet, non résolu à la fin de cette session.

**13. Deux pièges Git rencontrés et documentés** :
   - `git branch production origin/main` configure le tracking de la nouvelle branche locale sur `origin/main` par défaut (comportement Git surprenant : le point de départ étant une remote-tracking branch, Git l'utilise comme upstream) — corrigé immédiatement avec `git branch --set-upstream-to=origin/production production`, sinon un futur `git push` depuis `production` serait parti sur `main`.
   - Deux fois cette session, un commit vide poussé directement sur `production` (pour forcer un premier déploiement Vercel) a fait diverger `production` de `main`, cassant le `git merge main --ff-only` habituel (`Diverging branches can't be fast-forwarded`). Résolu à chaque fois par un `git merge main` classique (commit de fusion, sans risque de conflit réel), puis **immédiatement suivi d'un `git merge production --ff-only` sur `main`** pour ramener les deux branches sur le même commit et éviter que ça se reproduise. État actuel : `main` et `production` synchronisées sur `f7d5eed`.

## Ce que la session a découvert et qui ne vit dans aucun artefact

- **`railway connect <service>` ouvre un shell `psql` interactif dans la version CLI installée ici (4.35.1)**, pas un tunnel réutilisable — le flag `--tunnel-only` vu dans le dashboard Railway n'existe pas dans cette version. Pour scripter des migrations/imports depuis le poste local, on reste sur le pattern staging : activer "Public Access" sur Postgres pour obtenir une URL publique, l'utiliser en préfixe de commande (`DATABASE_URL="..." npx medusa exec ...`).
- **Le classificateur de permissions de l'environnement bloque de façon incohérente la lecture de `DATABASE_PUBLIC_URL` via `railway variables --kv | grep`** — parfois ça passe (lu directement pour staging plus tard dans la session), parfois bloqué (bloqué pour prod au début) sans changement de commande apparent. Pas de règle claire identifiée ; le contournement est de demander à l'utilisateur de coller la valeur depuis le dashboard.
- **Un service Railway fraîchement créé via GitHub n'apparaît pas dans `railway service status --all` tant qu'un premier déploiement n'a pas été lancé au moins une fois** (manuellement, depuis le dashboard) — le service existe mais reste invisible côté CLI jusque-là.
- **Les URLs d'images produits sont physiquement partagées entre local/staging/prod** : elles sont copiées telles quelles (chaîne de caractères complète, pas juste un nom de fichier) depuis la base locale vers chaque nouvel environnement via `export-menu-data.ts`/`import-menu-data.ts`. Un bucket R2 "dédié prod" ne changerait donc rien pour les images déjà là — seulement pour les fichiers uploadés après coup (nouvelles factures, nouvelles images ajoutées depuis l'admin prod).
- **Interfaces changées depuis la session du 05/08** : Cloudflare R2 (gestion des tokens API déplacée du bucket vers la vue d'ensemble R2), Stripe (nouveau flux générique "Créer une destination d'événements" à la place de l'ancien écran Webhooks dédié).
- **`workflow-engine-redis` a une forme d'options différente de `cache-redis`/`event-bus-redis`** (`{ redis: { redisUrl } }` imbriqué, pas `{ redisUrl }` à plat) — découvert par un crash au boot (`Cannot destructure property 'url' of '(intermediate value)' as it is undefined`), non documenté clairement dans les types TS de premier niveau, trouvé en lisant `loaders/redis.js` du package directement.
- **L'ID réel d'un provider de paiement Medusa** (`pp_stripe_stripe` ici) est visible directement dans `payment_provider` en base — plus fiable que de deviner le format depuis la doc pour construire l'URL de webhook (`/hooks/payment/<id sans le préfixe "pp_">`).

## Problèmes identifiés, non résolus

- **Déploiement automatique Vercel cassé pour la branche `production`** — le problème central sur lequel la session s'est arrêtée. Symptôme : un `git push origin production` redéploie Railway automatiquement (fonctionne à chaque fois) mais ne crée **aucun** déploiement Vercel, ni Production ni Preview (pas juste "ignoré", rien n'apparaît dans la liste). Reproduit trois fois de suite, y compris **après une déconnexion/reconnexion complète du repo Git dans Vercel** (correctif standard recommandé par Vercel, qui n'a pas résolu le problème). Hypothèse retenue : limitation liée au fait que l'environnement "Production" de Vercel suit une branche (`production`) différente de la branche par défaut du repo GitHub (`main`) — possiblement mal supporté sur le plan Hobby. **Solution proposée, pas encore actée par l'utilisateur** : une GitHub Action qui appelle automatiquement le Deploy Hook Vercel à chaque push sur `production`, contournant complètement le déclenchement natif de Vercel. Nécessite d'ajouter l'URL du Deploy Hook (visible dans Vercel → Settings → Git → Deploy Hooks, section "manual-production" déjà créée cette session) comme secret du repo GitHub. **En attendant, le contournement manuel marche à tous les coups** : POST sur l'URL du Deploy Hook.
- **Test de paiement réel en mode live jamais effectué** (checklist section 4, dernier point) — bloqué juste avant par la découverte du bug provider de paiement, puis la session s'est arrêtée sur le problème Vercel avant d'y revenir. **Prochaine étape immédiate de la prochaine session.**
- **Factures privées dans le bucket R2 public** — statut inchangé depuis le 10/08, toujours pas implémenté, et **prod hérite du même problème que staging** puisque le bucket est partagé. Toujours "à corriger avant accumulation de vraies données clients", pas un blocant dur.
- **Médiateur de la consommation** — inchangé, blocant légal dur avant l'ouverture des ventes, pas touché cette session.
- **Registre des traitements RGPD (art. 30)** — inchangé, pas touché cette session.
- **Aucun monitoring/alerting configuré** — inchangé, pas touché cette session.
- **Bascule DNS entièrement à faire** — rien commencé sur ce volet (TTL, ajout du domaine `kim-hi-noodle.fr` à Vercel, redirection www/canonical, coupure finale). `NEXT_PUBLIC_BASE_URL`/`STORE_CORS`/`AUTH_CORS`/`STOREFRONT_URL` pointent aujourd'hui vers le domaine provisoire `khn-prod.vercel.app` — **à reposer + redéployer** une fois le vrai domaine branché (rappel déjà connu : les `NEXT_PUBLIC_*` sont figés au build).
- **`docs/checklist-bascule-prestashop.md` pas mis à jour cette session** — plusieurs points de la section 3 et 4 sont maintenant faits ou avancés (voir ce handoff) mais les cases à cocher n'ont pas été touchées ; à faire en même temps que la prochaine session, une fois le test de paiement réel confirmé.
