# Formule Composants are curated via a link module; Sélections live in `line_item.metadata`

A Formule's Composants ("the entrée slot", "the plat slot") each list the Variantes explicitly curated into them, and the customer's Sélection — the Variantes actually picked — has to travel from cart to order, stay readable from the admin, and never be forgeable by the client. Medusa v2.16 has no bundle concept (ADR 0001), so both halves had to be modelled from scratch, and they get different answers on purpose: **Curation is administration data — rare, human-edited, and it must be correct; Sélection is transactional data — massive, machine-written, and it must follow its line.**

**Curation** is a custom `formule` module holding the Composants (`formule_product_id`, `key`, `label`, `rank`), with the allowed Variantes per Composant recorded as a Module Link, `defineLink({ linkable: FormuleModule.linkable.formuleComposant, isList: true }, { linkable: ProductModule.linkable.productVariant, isList: true })` — `ProductModule.linkable.productVariant` verified to exist at runtime against the installed package (`docs/research/2026-07-16-medusa-formules-composants-selection.md` §6.1). No price column on the link table, ever.

**Sélection** is one flat, primitive key per Composant on `line_item.metadata` — `formule_entree_variant_id: "variant_01J…"` — written from the storefront via `POST /store/carts/:id/line-items`, whose validator accepts `metadata` (`@medusajs/medusa → dist/api/store/carts/validators.js:58`). `completeCartWorkflow` copies it onto the order line verbatim (`@medusajs/core-flows → dist/cart/utils/prepare-line-item-data.js:54`) — the same mechanism ADR 0004 used for the Créneau, now proven end to end for line items too.

## What this rejects

The obvious worry, raised before this ADR was written: does `line_item.metadata` have the same trap ADR 0004 found in `shipping_methods[].data` — something that "works with no backend" and silently drops data on a client round-trip? **No.** `addToCartWorkflow` does merge lines that it considers identical, accumulating quantity (`get-line-item-actions.js:58-61`), but the merge key is `metadata`, compared **deeply**, and Medusa's own comment says so (`:60`, *"same variant_id, metadata and custom price"*). Two Formules with different Sélections produce two lines, not one merged line with a lost Sélection — verified by running the installed comparison function against realistic inputs (research note §1.3). The structural difference from `shipping_methods[].data`: that field was a bystander Medusa transported without reading; `metadata` is part of a line's identity. And where not resending `data` erased the Créneau, not resending `metadata` **preserves** the Sélection, because `{}` is not `isPresent` and never triggers a merge (`is-present.js:17-19`). The field defaults the safe way.

Two "free" candidates for **Curation** are rejected precisely because they are free: `product.metadata` is admin-editable natively, but only for primitive values (`EDITABLE_TYPES = ["string", "number", "boolean"]`, `metadata-form.tsx:329`) — a per-composant list of Variantes is inherently nested, so it would render disabled with *"use the API directly"* (`en.json:96`), which erases the one argument for choosing it. `ProductCategory` / `ProductCollection` / `ProductTag` are rejected because they range over `Product`, not `ProductVariant` — they cannot express "Samoussas Bœuf yes, Samoussas Légumes no", which is exactly the granularity ADR 0001 made non-negotiable — and categories are already claimed by the Carte's own structure (Entrée/Plat/Dessert/Boisson), so reusing them for Curation would grow a second, confusable category tree. Product Options/`ProductOptionValue` are rejected as a backdoor to the variant matrix ADR 0001 already ruled out — `ProductOptionValue.variants` names the variantes of the Formule itself, not the ones offered in a slot.

Two candidates are rejected on the money invariant from ADR 0001 (*a Sélection carries no money*). Child line items at 0€ are rejected because a price of zero is still a price, computed outside the Sélection's own line. Line-item adjustments are rejected because `amount` is non-nullable with a `>= 0` database check (`@medusajs/cart → dist/models/line-item-adjustment.js:13, 34`) — an adjustment is money by construction and is summed into the order total (`complete-cart.js:358`).

## Consequences

Two validator hooks become non-optional, because `line_item.metadata` is written by the client through a public route (`validators.js:58`) — an unvalidated Sélection is a field the customer controls, and Curation would be a UI suggestion, not a guarantee. `addToCartWorkflow.hooks.validate` rejects an incoherent Sélection immediately, with an error the client can act on. `completeCartWorkflow.hooks.validate` is the check that matters: it receives `cart.items[].metadata` (`complete-cart.js:292-295`, `fields.js:114`) and re-checks against the Curation at the moment that counts — a dish pulled from a Formule at 12:05 must not be sellable at 12:07, the same lesson ADR 0004 drew from a Créneau expiring mid-payment. It must check that every Composant is filled and that every chosen Variante belongs to the Curation **of its own Composant**, not of the Formule in general — this is the check that protects margin, and it is the entire reason ADR 0001 required explicit curation in the first place.

An admin widget on `order.details.before` is required, because a line item's metadata is worse off than the order's: the Metadata card only ever reads `order.metadata` (`metadata-section.tsx:21-25`), and no native admin route edits a line item's metadata at all (exhaustive grep of `get-route.map.tsx`). Without the widget, the Sélection is invisible outside a raw JSON dump, and CONTEXT.md's claim that the admin order list is the source of truth becomes false for what the kitchen needs to cook. Cost is near zero: the order page already loads `*items`, metadata included (`order-detail/constants.ts:47`) — no extra request, same shape as the existing `order-pickup-slot.tsx` widget.

An admin screen for Curation is the real cost of this decision, and it should be budgeted as such rather than discovered later — the `pickup` module (models, `src/api/admin/pickup/` routes, `src/admin/routes/settings/pickup/page.tsx`, components) is the exact, already-built precedent for its shape.

`formule_composant.key` is a contract once a first order exists: it is the string that ends up in `line_item.metadata` (`formule_entree_variant_id`). Renaming a key after that orphans every Sélection already placed, since orders are frozen and Curation is not — treat `key` as immutable post-creation.

**Exit cost and triggers, named on purpose.** `line_item.metadata` cannot be queried across orders — "how many Menus Midi with Samoussas Bœuf this month" has no answer today. That is fine: orders are same-day (CONTEXT.md, *Commandes fermées*), and a service is a few dozen rows. The day that stops being true — someone wants a cross-service popularity report or a purchasing forecast — the Sélection migrates to a linked module, and the migration is a script reading `order.items[].metadata.formule_*_variant_id` off existing orders, joined on `formule_composant.key`; nothing written here is thrown away. Separately: this model makes a priced Supplément (CONTEXT.md, *Not in the domain*) structurally impossible to bolt on without reopening ADR 0001 — a Sélection in metadata cannot carry a price, by design, so a future "+2€ magret" forces a deliberate decision rather than an ad-hoc field. That is this decision's best property, not a limitation to route around.
