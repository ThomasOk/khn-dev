# The Carte's Rang lives in `product.metadata`, scoped to the Produit

The Carte's Sections already follow an order the restaurateur owns — `ProductCategory.rank`, reordered by drag & drop in the Medusa admin, read and sorted on at page level (`apps/storefront/src/modules/store/templates/index.tsx`). The Produits *inside* a Section follow no order at all: `CarteSection` calls `listProducts` with no `order` parameter, so Medusa's default applies and dishes come out in creation order — which is to say, in the order somebody happened to type them into the admin.

That order is editorial. The signature dish goes first, the one the restaurant wants sold sits at eye level, and the "Assiette découverte" belongs above the plain nems whatever the alphabet or the price says. No rule over `title`, `created_at` or `calculated_price` expresses it, so sorting by one of those would only trade an accidental order for a different accidental order. The spec *Commander depuis la page Carte* already settled the same argument one level up — « L'ordre d'une carte de restaurant n'est pas cosmétique et appartient au restaurateur » — and the reasoning transfers whole to the dishes.

Medusa 2.16 has nothing to switch on. `ProductCategory.products` is a plain many-to-many and **the pivot carries no rank** (`@medusajs/product/dist/models/product-category.js`), unlike `ProductCategory.rank` itself. There is no column, so there is no native screen either: the Rang has to be modelled here.

**Decided: the Rang is one number per Produit, stored as `product.metadata.carte_rank`, written densely as `0…N-1` across a whole Section by an admin widget, and applied by sorting in memory in the storefront.**

## Why `metadata`, when ADR 0005 argued the opposite

ADR 0005 rejected `product.metadata` for the Formule Curation and built a module instead. A reader who finds that ADR and then finds a rank sitting in `product.metadata` will reasonably conclude somebody took a shortcut. They did not, and the two decisions turn on the same question asked of different data: **what does a wrong value cost?**

A wrong Curation lets a premium dish into a fixed-price Formule and loses margin silently, order after order, with nothing on any screen saying so. That earned a module, a Module Link, and two validator hooks. A wrong Rang shows the soup above the nems. The restaurateur sees it on the storefront immediately, drags it back, and the incident is over. Nothing is lost, nothing is unrecoverable, and no invariant is broken — a Rang protects no money and guards no rule, which is precisely why it does not deserve the apparatus that protects one.

The specific objection ADR 0005 raised against metadata is also **absent here**, and that matters more than the general argument. It rejected metadata because the admin's native editor only handles primitives — `EDITABLE_TYPES = ["string", "number", "boolean"]` (`@medusajs/dashboard/dist/chunk-NMMOPJ26.mjs:301`) — so a per-Composant list of Variantes would have rendered disabled with *"use the API directly"*, erasing the one argument for choosing metadata at all. A Rang is a number. It is natively editable in the admin product form as Medusa ships, with no code, which makes metadata's cheapness real rather than theoretical.

**Rejected: a `carte` module holding `(product_id, rank)` joined by a Module Link.** It buys a typed column and a foreign key for one integer per dish, and it costs a model, a migration, a link, admin routes, a service and a second place to look when a dish is out of order — the `formule` module's full weight, spent on a field that carries no invariant. The Carte is thirty-four Produits across six Sections; this is not the scale at which a real column starts paying for itself.

Two costs of metadata are accepted knowingly. **It is public**: `listProducts` already requests `+metadata` (`apps/storefront/src/lib/data/products.ts`) and hands the whole Produit to the browser, so the Rang ships to every visitor. Harmless for a display order, and a standing reminder that `product.metadata` is not a place for anything unpublishable. **And nothing validates it**: no schema stops `carte_rank: "trois"` typed into the raw metadata form, and nothing enforces uniqueness. The sort therefore has to survive garbage rather than assume its absence — see *Consequences*.

## Why one Rang per Produit, and not one per (Produit, Section)

The more faithful model is a Rang on the *placement*: a Produit reachable from two Sections would sit in a different position in each, since order genuinely is a property of where a dish appears, not of the dish. Medusa permits that membership — the Carte spec already deduplicates for it — so the modelling question is real.

It is refused anyway. On a restaurant carte a dish sits in exactly one Section: a Pad Thai is a plat, and it is not also a dessert. Verified against the live data — the Carte is entirely flat, six root categories (Entrées 6, Plats 12, Soupes 4, Desserts 4, Formules 6, Boissons 1), no sub-category anywhere, every Produit in exactly one. A composite key would buy a capability the domain does not ask for, at the price of an admin surface that edits a relationship rather than a dish, and an orphan-cleanup question every time a Produit leaves a category.

**The tripwire this leaves, stated so it is met as a documented limit rather than as a bug:** the widget renumbers a whole Section densely, but the field it writes is scoped to the Produit. A dish belonging to two categories would have its Rang overwritten by whichever Section was reordered last, silently shuffling it in the other. Unreachable today — the tree is flat — and it becomes reachable the moment a sub-category or a cross-listing Section ("Nos suggestions", re-listing dishes from elsewhere) is introduced. That is the trigger to reopen this decision, and the migration is the one named at the end of this ADR with a Section key added to the key.

## Why the sort runs in memory, in the storefront

`order=metadata.carte_rank` does not work and should not be attempted: `buildOrder` splits an order string on `.` and builds a nested object (`@medusajs/utils/dist/common/build-query.js`), so `metadata.carte_rank` is read as a *relation* named `metadata`, not as a JSON path.

This costs nothing. `CarteSection` already fetches its whole Section before rendering (`limit: 100`, and the spec removed pagination from the Carte on purpose), and the category pages already fetch 100 and sort in memory through `sortProducts` before paginating. The machinery exists on both surfaces; the Rang is a new case inside it, not a new mechanism.

## Consequences

**A Produit with no Rang sorts last, and so does a Rang that is not a number.** Three rules, and they are the contract: a numeric `carte_rank` wins; a missing or non-numeric one is treated as absent and goes to the end; equal Rangs tie-break on `created_at`, the order that governs today. The first consequence is the valuable one — on the day this ships **no Produit carries any metadata at all**, so every dish falls through to the tie-break and the Carte renders exactly as it does now. The change is a visible no-op until the restaurateur moves something, which is the property to want from a feature that touches every page of the menu. Sorting unranked dishes *first* was rejected for the mirror reason: it would reorder the whole Carte on deploy day, and would thereafter place every new dish ahead of the one the restaurateur deliberately put first.

**Dense `0…N-1`, rewritten across the Section on every drop.** Sparse numbering (`10, 20, 30…`) and fractional insertion both exist to avoid mass-rewriting thousands of rows, and the largest Section here is twelve dishes. Dense numbering earns something they do not: after any drop the Section's Rangs are exactly `0…N-1`, which makes duplicates structurally impossible through the widget and keeps "unranked" unambiguous — the sort contract above is enforced by construction rather than by hope. The write is one `POST /admin/products/batch` (`@medusajs/medusa/dist/api/admin/products/batch/route.js`, running `batchProductsWorkflow`), not N requests.

**The widget must read-modify-write `metadata`, never send `{ carte_rank }` alone.** A product update replaces the metadata object wholesale. Harmless today, since no Produit carries any other key, and destructive the day the unimplemented `availability` work or anything else writes there. This is the kind of trap that is free to avoid now and expensive to diagnose later.

**Both the Carte and the category pages obey the Rang.** `/categories/plats` renders the same dishes as the *Plats* Section of the Carte; letting them disagree means the restaurateur drags a dish to second place, watches it move on one URL and finds it eighth on the other, with nothing on screen explaining why. The Rang becomes the default sort on the category pages, joining their existing refinement as a fourth entry rather than replacing it. Whether a price/date refinement belongs on a restaurant site at all is a separate question about what those routes are for.

**The editing surface is a drag & drop widget on the category detail page** (`product_category.details.after`), saving on drop with optimistic rollback, in the idiom the five existing admin surfaces already use. The category page is where the Section is already defined and where its own Rang is already dragged, so the gesture is the one the restaurateur has learned, one level down. It requires declaring `@dnd-kit/core`, `@dnd-kit/sortable` and `@dnd-kit/utilities` in `apps/backend` — **not new dependencies**: `@medusajs/ui` already declares all three directly, and the declaration only makes reachable, under pnpm's strictness, packages the install already brings in at matching versions. There is nothing to reuse beyond that: `@medusajs/ui` exports no sortable list, and its own `@dnd-kit` usage is DataTable **column** reordering.

**The arithmetic is tested, the comparator is not.** Turning a reordered array into a dense batch payload goes in `src/admin/lib/`, beside `formule.ts` and its unit spec, picked up by the existing `**/src/**/__tests__/**/*.unit.spec.[jt]s` matcher — the seam and the precedent both exist, and that is where off-by-one errors live. The storefront comparator stays manually verified, on the same bar the Carte spec set for opening the storefront's first test runner. The one branch that does not fail loudly is the unranked path, which fires weeks later when a dish is added; it is covered by an explicit one-off check at implementation rather than by standing up a runner for ten lines.

**A sixty-second `revalidate` is added to the product fetches, and it is a mitigation, not a design.** The storefront caches products with `cache: "force-cache"` and a tag built from `_medusa_cache_id`, a **per-visitor** UUID cookie minted in `middleware.ts` — so no server-side actor can enumerate the tags to invalidate, and the only `revalidateTag` for products in the codebase fires on a locale switch (`apps/storefront/src/lib/data/locale-actions.ts`). Without a bound, a Rang change would never reach the storefront, and `next dev` would hide it perfectly until the first deploy. Sixty seconds converts "stale forever" into "stale for a minute", which is inside a restaurateur's patience for *I reordered the carte, let me go look*. It does not fix the per-visitor tagging, which is a cache-architecture problem spanning cart, customer, orders and regions, and which deserves its own decision rather than being smuggled in behind a display feature.

**A Rang means display order and nothing else.** It is editorial, never derived — nothing computes it, on the side of the Annonce and the Mode vitrine rather than Hors carte and Commandes fermées. It carries no promotion, no *mise en avant*, no priority in any other part of the system, and the first Produit of a Section is not "featured" anywhere. Written down because "the first dish" is exactly the kind of handle a later feature will be tempted to grab.

**Exit, named so it is not re-derived.** If the Rang ever needs to become a real column — a cross-listing Section, a per-placement order, or a volume that makes in-memory sorting untenable — the migration is a script reading `product.metadata.carte_rank` off existing Produits into a `(product_id, rank)` model, with a category key added if the move is what forced it. Nothing written here is thrown away, and the storefront comparator is the only reader to repoint.
