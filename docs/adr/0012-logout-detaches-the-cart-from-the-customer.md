# Logout detaches the cart from the customer through a new store route

Ticket 09 ("la déconnexion garde le panier") keeps the cart alive past logout instead of wiping it: the cart the customer composed stays orderable, as a guest cart, until payment. That is the whole of what the spec originally asked for, and by itself it is a two-line change to `signout()`.

It is not enough by itself. Medusa's native login-time transfer (`transferCartCustomerWorkflow`, reached through `POST /store/carts/:id/customer`) pins `customer_id` and `email` onto the cart record itself, not onto the request session. Nothing native ever clears that. So the moment the cart survives logout, it survives *with* the departed customer's identity still attached — and a guest checkout completed later on that exact cart still carries that `customer_id` straight onto the resulting order (`complete-cart.js`: `customer_id: cart.customer?.id`). `sync-customer-billing-address-from-order` (ticket 03) then reads that order's `customer.has_account` and silently overwrites the departed customer's saved billing address with whatever the next, unauthenticated person typed in.

This is not a shared-device curiosity. It is reachable through the exact round trip this ticket's own acceptance criteria require testing: compose a cart, log in, log out, order as guest. Confirmed with a real HTTP-level integration test before this ADR was written: a second, unauthenticated person completing the same cart renamed the first customer's account and overwrote their saved address, with no login on their end at all. That directly breaks User Story 33 ("qu'une commande passée en invité n'écrive rien sur aucun Client") for what is meant to be the ticket's primary flow, not an edge case.

## Why a new store route, against User Story 36

User Story 36 asks that no new API route be created for this feature; everything was meant to rest on native routes already installed. There is no native route that clears a cart's `customer_id` once transferred — the only native cart/customer route is the one-directional `POST /store/carts/:id/customer`, and the store update-cart route's own validators don't even accept `customer_id` in the body (`@medusajs/medusa`'s `UpdateCart` schema omits it entirely). Closing the leak natively is not available; closing it at all requires a workflow that can call `cartModuleService.updateCarts()` directly, and a route to invoke it from the storefront's `signout()`.

This ADR records that exception deliberately: `DELETE /store/customers/me/carts/:id/customer` (`apps/backend/src/api/store/customers/me/carts/[id]/customer/route.ts`, backed by `detachCartCustomerWorkflow`) is the one new route in the compte-client epic. It was chosen, mid-implementation, over shipping the literal two-line fix with the leak left open — the data-integrity cost (a customer's saved address silently corrupted by a stranger's checkout) outweighs the "no new routes" convention in this one case.

The route is scoped as narrowly as the constraint allows: it lives under the natively auto-authenticated `/store/customers/me/*` wildcard (no bespoke auth middleware), and the workflow itself checks that the cart it's asked to detach actually belongs to the calling customer — a mismatch is refused (`MedusaError.Types.NOT_ALLOWED`), never silently ignored. A cart already detached, or never attached, is a no-op, so the storefront can call it unconditionally on every logout without needing to know the cart's prior state.

## Consequences

Story 36 is no longer literally true for this epic; a future reader of `docs/specs/compte-client.md`'s "Ce qui n'est pas créé" section who takes it at face value should find this ADR instead. The exception is narrow and single-purpose: one route, one workflow, both doing nothing but reversing a native side effect this feature reintroduced by design (keeping the cart alive past logout).

The workflow's compensation restores the cart's prior `customer_id`, `email`, `shipping_address` and `billing_address` if a later step in the same workflow fails — it does not, and cannot, restore state once the workflow has committed and a *different* request has since mutated the cart (e.g. a guest checkout that ran between a detach and a hypothetical rollback of some unrelated, later operation). That is the same boundary every other workflow in this codebase accepts.
